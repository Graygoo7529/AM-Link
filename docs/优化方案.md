# Add/Search 优化方案（Evidence-first Hybrid Memory）

本文是对 [设计理念.md](../设计理念.md) 的实施化补充。它保留原始事件为事实真源、结构化 memory links、版本化事实、user_id 隔离、Search 只返回证据和模型故障降级等基本思想，重点解决当前版本的结果重复、时间语义、请求关键路径和可验证性问题。

## 目标与非目标

目标是让有限 `top_k` 中的结果更少重复、更容易追溯、更符合当前/历史语义，并在模型或 embedding 不可用时仍然可用。

本阶段不引入自由循环 Agent，不让 Search 生成答案，不改变主办方 Add/Search JSON 协议，也不把 Markdown 作为事务真源。

## 目标架构

```text
ADD
  schema/auth -> raw + daily + FTS + working memory 原子提交
                    |
              立即可检索
                    |
  增量维护：时间/实体预处理 -> 受限模型 mutation -> 版本/链接事务
                    |
              embedding + Markdown 投影

SEARCH
  query/options 规范化
      -> lexical + semantic + 时间/状态候选
      -> evidence group 归并与去重
      -> 复杂查询的受限 query plan
      -> typed-link 一至两跳扩展
      -> RRF、状态、时间、置信度和多样性重排
      -> 仅返回已有证据
```

## 数据模型增强

### 原始事件

`raw_events` 继续不可变，保留 role、原文、source timestamp、session 和 request 来源。原始事件和 daily 节点始终是降级检索的最低保障。

### 结构化节点

在 `memory_nodes` 上增加两个派生字段：

- `canonical_key`：包含 subject/predicate/value 的完整事实身份，用于合并同义改写；同一属性的不同值必须使用不同 key，并通过 supersedes 保留版本；
- `evidence_group_id`：同一事实及其支持证据的归并标识，用于 Search 结果去重。

旧数据库通过启动时迁移补齐字段，旧记录使用稳定的 memory ID 作为兼容默认值。时间相关节点另外保存 `time_expression`、`resolved_time_start`、`resolved_time_end` 和 `time_precision`；没有可靠锚点时只保存表达式，不虚构绝对日期。

结构化节点仍使用 `active`、`superseded`、`tombstoned` 状态，并通过 `source_event_ids` 追溯原始证据。后续模型 mutation 可以增加 `merge_into`、`contradicts` 和 `time_expression`，但任何引用都必须由 Repository 校验。

## ADD 技术路线

### 硬提交阶段

HTTP 200 前必须完成：鉴权、幂等校验、原始事件、daily/raw 节点、FTS、working memory 和请求记录。完成后即使外部模型不可用，Search 也能返回原始证据。

### 增强阶段

在有限预算内执行：

1. 从 source timestamp、明确日期和相对表达构造时间提示；
2. 以本次事件、working memory、相关节点和一跳 links 为上下文调用一次受限 `gpt-4o-mini`；
3. 对 JSON schema、source ordinal、user scope、节点状态和数量上限做校验；
4. 在同一事务中 upsert fact/entity/concept、typed links、supersedes/tombstone；
5. 增量写入 embedding 和 Markdown 投影。

`sync` 是默认增强模式，保持现有部署行为；`async` 模式在硬提交后写入持久化 enrichment job，由生命周期内 worker 消费。任务保留 `pending/running/completed/failed` 状态，失败使用退避后重试；启动时超过 5 分钟的 running job 回收为 pending，进程重启后可从数据库继续消费，不能依赖内存队列作为唯一任务记录。

## SEARCH 技术路线

### 候选召回

使用三路候选：

- FTS/BM25 和必要的 LIKE fallback，保障姓名、数字、否定词和原文短语；
- `embedding-3` 语义召回，解决同义表达和跨轮次关联；
- typed-link 图扩展，最多两跳、每个种子限制 fan-out，并按 query 相关性过滤。

中文 token 采用连续词、二元片段和数字/日期高权重的轻量策略；不依赖额外自由 Agent。

### 证据归并

召回结果先映射到 `evidence_group_id`，同一 canonical fact 的重复维护不会重复占满 top-k。raw event 保持独立直接证据；entity/concept 使用各自的稳定 group，多跳问题才补充关系链中的必要节点。最终允许同一事实最多保留一个结构化 fact 和一个必要的原文证据。

### 查询计划与重排

query planner 只输出检索扩展、候选 ID 和 intent（current/historical/temporal/multi-hop/general），不输出答案。最终排序综合 lexical、semantic、graph、model preference、时间有效性、状态、置信度、activity 和 group 多样性。

当前问题默认优先 active；历史问题允许 superseded；tombstoned 节点永不进入候选。

## 时间与事实版本

事件 timestamp 优先于模型推断；原文中的相对时间必须保留。确定性解析支持明确日期、今天/明天/昨天、上下周星期和上下月；相对表达只有在 source timestamp 可用时才生成候选日期范围，不覆盖原始文本。事实冲突通过 `valid_from/valid_to`、`supersedes` 或 `contradicts` 表达，Search 根据 intent 和时间范围选择当前或历史版本。

## 可靠性与成本控制

- Add/Search 的 provider 重试共享请求级 deadline，不能因两次重试叠加到不可控时长；
- 模型和 embedding 使用并发上限、429/5xx 退避和失败降级；
- 日志只记录 request ID、user 哈希、阶段、耗时和错误类型；
- 小规模评测继续使用 SQLite/WAL 和 brute-force 向量扫描，规模达到阈值后再迁移共享向量索引；
- 暂不使用 pi SDK。公开回放证明多步骤 Agent 的收益超过延迟、成本和不确定性后，再考虑增加固定步数的受限编排。

## 验收指标

每次公开数据回放记录：

- `evidence_recall@1/5/10`、MRR 或 nDCG；
- 多跳链覆盖率；
- current/historical 时间状态准确率；
- 重复证据率和 evidence group 多样性；
- Add/Search 的 p50、p95、错误率、provider 调用次数和 token 成本；
- provider 故障时的 raw evidence 可用率。

只有公开回放和并发压测完成后，才冻结正式 Full 配置和提交 commit。
