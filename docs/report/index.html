题目到底在考什么

LongMemEval 主要问：在很长的历史里，能否找到旧事实、判断当前状态、计算时间，或者在没有答案时诚实拒答。它把“找到一句相关话”与“找到足够回答的问题证据”区分开。

LoCoMo 把重点放在多次会话中的人物、事件和共同兴趣；PerLTQA 让关系方向、事件日期和原文冲突变得可见；MemoryAgentBench 则把最新值和多跳关系放在同一个材料里，测试系统是否会沿着链路继续走。

长历史与状态变化是什么意思

长历史不是单纯增加 token。BEAM 的 100K 到 10M 档、LongMemEval 的几十段会话，会让相似但无关的材料变多，真正有用的句子可能被预算、排序或摘要遮住。

状态变化指同一属性会有旧值、新值、冲突、过期或撤回。B01 的配额是明确更新，B02 的 Key 是无法解释的矛盾；两者都出现了“后来的句子”，却不能使用同一种覆盖规则。

不同数据集的“难”，落在不同位置

BEAM 关注历史规模、顺序和长期状态；LongMemEval 关注跨会话、时间、更新、拒答和聚合；LoCoMo 关注人物之间的多跳关系；PerLTQA 和 MemoryAgentBench 关注结构化关系、版本和冲突；CL-bench Life 关注规则、条件和缺失信息；PersonaMem-v2/v3 关注偏好、敏感字段、遗忘以及“提问之后才发生的反馈”。所以同一个 Search 分数，不能代表这些题型都处理得一样好。

分享时可以把它们想成不同的检查：有的问“记不记得”，有的问“记得哪一个版本”，有的问“记得谁的”，有的问“还缺哪个条件”，还有的问“这件事是否根本不该进入长期记忆”。

两个容易混淆的词

跨会话不是把一段很长的对话塞进上下文，而是当前问题发生在这次会话，答案却要从以前几次彼此独立的会话中拼出来。LM04 的链条、车灯和头盔分别出现在不同历史片段里；系统必须知道它们属于同一个问题，又不能把车灯的重复提及误算成第二次消费。

知识更新也不是把旧句子删除。B01 中每天 1,000 次后来变成 1,200 次，回答“现在”时要选新值，回答“最初”时又要能找到旧值。B02 的两种说法没有明确的替代关系，应该保留冲突并请求澄清。换句话说，记忆要保存事实，也要保存事实之间的时间和关系。

一个数据样本通常要拆成四个抽屉

History · 记忆输入

对话、事件、代码、评论或结构化事实；保留角色、日期和来源。

Task · 当前问题

question、query 或待完成任务；驱动 Search，不是历史事实。

Annotations · 评估侧

answer、evidence、rubric；用来核验，不能泄漏给 Add。

Auxiliary · 辅助字段

user_profile、生成计划、未来反馈标签；先检查是否真的对话中可见。

Add · 历史

sessions[].turns[]
每条 turn 保留来源 ID、speaker、content 与时间；来自 48 段会话。

Search · 当前任务

tasks[0].input.text
“我今年以来在自行车相关项目上总共花了多少钱？”

Eval · 只用于核验

annotations.answer = $185
evidence_turn_ids 指向 4 条来源 turn；这些字段不得进入 Add。

因此，同一个 JSON 里可能同时有“历史事实”和“答案标签”；预处理必须按字段分流，不能整条对象一起喂给记忆系统。
