# 一期实验与工程经验

这是一期复盘，不是二期协议。依据为冻结代码、历史记录及本次重新读取的公开 LoCoMo 自测报告；正式数据不用于本次分析。官方 Smoke 已通过、Full 已完成，具体官方名次和分数尚未登记。

## 接口如何落地

一期以 FastAPI 提供同步 JSON 接口，部署启用 Bearer 鉴权。Memory System Key 由我们提供给官方；Eval Key 由官方发给参赛者，用于操作评测平台，两者不同。

| 接口 | 一期约定与实现 |
| --- | --- |
| `POST /v1/memory/add` | 接收 `request_id/messages/user_id/session_id`；消息含 `role/content`、可选毫秒 `timestamp`。成功返回 `success: true` 并原样回传三个 ID |
| `POST /v1/memory/search` | 接收 `query/user_id/top_k`、可选顶层 `options`；返回 `{"data":[...]}`，每项有稳定 `id` 和 `content`，可选 `score/created_at` |
| `GET /health` | 无鉴权返回 200；这是存活检查，不证明模型或检索质量正常 |

原文、近期记忆和全文索引事务提交后才返回 Add 成功。相同用户、相同请求 ID 和相同内容重复提交返回已保存响应；内容冲突返回 409。Search 按用户隔离、相关性排序，最多返回 `top_k` 项，正式使用 100。没有实现异步状态查询地址。

实现保留原始空白、角色和顺序，不把来源会话当作检索隔离边界。模型故障时一期会返回原文检索的降级结果，存储暂时失败才显式返回 503。这个差别是二期必须重新审视的成功语义。

## 数据与效果

公开 LoCoMo 原始集有 10 段长对话，包含多轮会话、时间信息，以及带来源证据的问答。我们按会话分块写入，把问答的证据标识映射回原文，测量证据 Recall/MRR；剔除无法解析的证据标注。它不同于官方 LoCoMo-Refined，也不能覆盖官方全部记忆治理、规则和个性化任务。

下表取自现存报告，全部是本地证据检索自评，不是官方分数。指标仅在同一组切片内部比较。

| 对照与规模 | Recall@10 | MRR | 结论 |
| --- | ---: | ---: | --- |
| 10 对话词面基线，399 Add / 480 Search | 0.366417 | 0.235646 | 快速、可复现的起点 |
| 同样本改进词面检索与稳定排序 | 0.439438 | 0.292152 | 改进有效；两次新库回放的查询结果一致 |
| 2 对话局部切片，10 Add / 18 Search，词面检索 | 0.592593 | 0.506635 | 真实模型对照的基线 |
| 同切片真实 LLM + embedding，新库写入 | 0.675926 | 0.607885 | 总体召回改善，但多跳完整链覆盖仍为 0 |
| 同增强库上的来源证据提升回放 | 0.662037 | 0.618546 | 排序指标各有升降，不能笼统称为全面改善 |

对应报告分别为 `locomo-balanced-report.json`、`locomo10-determinism-{a,b}-report.json`、`locomo-provider-expanded-lexical-report.json`、`locomo-provider-expanded-report.json`、`locomo-provider-evidence-boost-report.json`，已复制到被忽略的 `archive/phase-1/data/reports/`。最后一组 Add 耗时仅毫秒级，是已存在数据的重放，不能拿它证明真实增强写入延迟。新库增强组 Add p95 约 9.94 秒，Search p95 约 9.87 秒。

历史互补 evidence group 选择实验记录：真实 provider 录制/回放 A/B 的 Recall@10 从 0.861111 降至 0.638889，MRR 从 0.624417 降至 0.574264；因此删除实验，没有部署。该结论来自[历史复盘](../../archive/phase-1/docs/扩大验证与可靠性优化.md)，本轮未重跑，也未找回该真实 A/B 原始报告；不要与上表的 18 题结果混为同一次对照。

判断：链接能够补来源和关系，但链接数量增加不等于推理证据齐全；机械追求多样性会挤走真正相关证据。下一期应分别测直接命中、完整证据链、历史状态、噪声影响和空结果正确性，而非只看一个平均 Recall。

## 架构与编码

一期分为协议校验、写入/检索编排、事务存储、模型适配、结构化整理、图与时间检索、离线回放。SQLite/WAL 保存真源，全文索引、向量和 Markdown 为派生视图。LLM 参与结构化整理与检索计划，链接展开由确定性程序完成，不依赖完整 Agent SDK。

值得保留的实践：

- 将持久化事实与派生索引分开；所有链接、缓存、索引都带用户作用域。
- 修改事实前校验来源、可修改范围与版本；更新后仍能找回历史证据。
- 模型适配与业务解耦，记录模型、提示版本和调用阶段，便于真实 provider 对照。
- 同分结果使用稳定排序；回放固定输入、新建数据库，避免缓存与历史状态污染比较。
- 测试校验行为：立即可检索、重复投递、用户隔离、来源追溯、并发、超时和不完整结构化输出。

需要收缩的复杂度：存储和编排代码逐步承载了过多队列、维护、恢复与重建状态；增加接口数量不等于职责清晰。二期先画出一次请求的必要状态和提交边界，再按边界组织模块，不预先建立通用任务平台。

## 最重要的教训：重试不应在请求结束后继续扩张

一期同时有 provider HTTP 重试、结构化格式修复、持久化增强任务重试。即使使用同步 Add，后台 worker 仍会轮询失败任务。恢复某个旧任务可能重建整位用户的向量索引；若维护水位已经推进，LLM 可能不再执行，但 embedding 仍重新计算。这解释了评测完成后 embedding 费用继续增长、两类模型调用量不一致的机制。

2026-08-08 的运维检查曾发现约 1,773 个可重试失败任务。随后把服务器 `AML_ENRICHMENT_MAX_ATTEMPTS` 从 5 改为 1，阻止失败任务继续被后台挑选；它是包含首次尝试的任务上限，**不是** provider 的 HTTP 重试次数，也不是完整的费用开关。归档代码默认仍为 5，服务器最后配置为 1，不能混淆。

二期应采用的约束：

1. 正常服务仅在收到请求时做必要工作，默认无自动补偿 worker、无自动全用户重建；离线重建必须是有预算、可停止的显式操作。
2. 按官方约定，暂时性依赖故障返回 429/503/504 等明确错误，让官方做有界重试。内部模型调用默认不重试，确有证据才考虑单次请求内的极少量重试。
3. 先定义成功所需的阶段。幂等记录只缓存真正完成的成功；若原文已保存但必要索引失败，相同请求重来应续做缺失阶段，不能因已有原文直接返回缓存成功，也不能重复处理已完成阶段。
4. “确实没有证据”可以返回空数组；“模型或存储不可用”不应伪装成空数组。允许哪些降级结果必须提前声明并测试，不能静默变成另一种参评方法。
5. 截止时间覆盖排队、上游调用和存储；客户端断开、请求超时、服务停止时不应留下无人管理的模型调用。官方取消任务不能自动取消已经发到我们服务器的请求。
6. 记录请求级实际调用次数、tokens、耗时和失败阶段；增加停流后零新增 provider 调用的验收。HTTP 200、健康检查或供应商控制台的一张图都不足以证明业务正常。

单任务有限次重试仍会在大量积压与整用户重建下放大费用。可靠性需要明确失败、幂等与可观测性，不需要默认持续后台补偿。

## 验证边界

一期无模型并发测试完成 64 次不同用户 Add、32 次幂等重放及 256 次 Search；这证明本地协议与存储路径可用，不证明真实 provider 能承受同样并发。归档复核 61 项测试通过，存在一条 TestClient 依赖弃用警告。二期应先用小规模真实 provider 故障与并发实验验证，再申报容量。
