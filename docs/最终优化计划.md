## 不变边界

原始消息仍是事实真源；结构化节点、links、embedding 和 Markdown 都是可重建派生物。Add 必须在返回 HTTP 200 前完成最低可用持久化并可立即 Search。Search 只返回已有记忆和来源证据，不生成最终答案，不跨 `user_id`，不使用答案或评测金标。

外部协议不变：Add 继续接收 `request_id/messages/user_id/session_id`，Search 继续接收 `query/options/user_id/top_k`，并只返回赛事允许的 `data[].id/content/score/created_at`。

## 从 TinySoul 提炼的机制

TinySoul 的完整 Memory 是面向长期 Agent 生命周期的五类 Markdown、活动 Memory、渐进 action 和独立 Maintenance Turn；比赛服务只有一次 Add 和一次 Search，不能原样搬运。但以下机制可以收敛到内部实现：

1. **先发现、再修改**：TinySoul 要求 Maintenance 先 inspect/recall，再 create/rewrite/redirect。比赛版改为由 Repository 先召回有限结构节点，LLM 只能 supersede/tombstone 本轮已召回的稳定 ID。
2. **稳定身份优先于摘要文本**：向维护模型公开 `memory_id/canonical_key/version`，相同事实优先复用原身份和 canonical key，避免平行事实。
3. **Inspect 与 Recall 分工**：TinySoul inspect 返回有界候选、正向引用和 backlinks，recall 才读取完整证据。比赛版在 Search 规划前执行一次确定性一跳 inspect，规划后对选中的节点执行最终有界图扩展；返回内容仍是节点内已经保存的证据正文。
4. **Link 是检索结构，不是展示装饰**：模型规划器能够看到一跳邻接候选并选择其稳定 ID；被选择的 link 成为最终扩展的优先种子。
5. **派生能力可降级**：LLM、embedding 或 link inspect 失败时继续使用 raw/FTS；任何可选路径都不破坏协议和立即可检索性。

## 本轮实现

### Add maintenance

- maintenance payload 增加已有节点的 `canonical_key/evidence_group_id/version/confidence/activity/source_event_ids`。
- payload 明确列出 `mutable_memory_ids`，模型只可在这些已召回节点上执行 supersede/tombstone。
- 模型响应通过 schema 后再次进行作用域校验；越界 mutation 整次拒绝，raw evidence 保持可检索并记录 maintenance failure。
- 首次响应只有在 JSON schema 校验失败时允许一次字段级修复重试；第二次仍失败即降级，不形成自由循环。
- prompt 强调复用已有 canonical key 和实体/概念名称，只有现有候选不能表达新事实时才创建新身份。

### Search

- 直接 lexical/semantic/temporal 初召回后，从有限种子执行一次一跳 link inspect。
- Query planner 的最多 40 个候选同时包含直接候选和一跳 link 候选，并标明候选来源和 kind。
- planner 扩展词重新组成 embedding query；失败则保留首次 semantic 结果。
- planner 选择的 link ID 进入最终 graph seed 的最高优先级。
- 普通查询最多两跳；明确 `multi_hop` 查询最多三跳，以覆盖 `raw -> fact -> entity/concept -> fact` 的实际拓扑，仍限制种子、fan-out、候选总量和请求 deadline。

## 验收门槛

1. 原有协议、幂等、隔离、tombstone、历史状态和 deadline 测试全部通过。
2. 新测试证明未 inspect 的同用户 ID 也不能被模型修改。
3. 新测试证明一跳 link 候选进入 planner、preferred link 成为最终候选。
4. 新测试证明 planner 扩展触发第二次 embedding，但失败可降级。
5. 新测试证明 multi-hop 使用三跳，普通查询保持两跳。
6. 局部 LoCoMo 不要求一次实验决定正式收益；至少记录同一 manifest 的成功率、Recall@10、MRR、chain coverage、延迟与 provider 调用数。

## 不做事项

- 不把 TinySoul 的 `note`、文件事务 journal、每日归档和 Agent action API 移植到比赛服务。
- 不在 Search 中引入自由 LLM 循环或最终回答生成。
- 不在截止前替换 SQLite、HTTP 框架、provider 或外部协议。
- 不用公开题目、答案文本或数据集身份构造专用规则。
