# 当前方法的全量 100 题复核计划

## 目的

在不覆盖历史运行的前提下，以全新运行身份重放公开准备的 26 个独立历史，完成 780 个 Add 和 100 个 Search，并在本地用较强 Answer 做诊断。目标是区分：

1. Add/Search 协议是否稳定；
2. Query、预览、Select、闭合和最终装箱各自丢失了哪些证据；
3. 多轮模型调用之间是否保留了同一问题的检索意图；
4. 当前 Select 改动是否值得继续，还是需要先重构可见语境。

## 清理边界

历史 `research/benchmark/data/runs/`、旧研究页面和已登记分母保留。全量复核使用 `fresh32-*` 新运行目录；每个目录拥有独立的 `memory.sqlite3`，不读取默认库或旧运行库。这是实验数据的逻辑清空，保证结果从空记忆开始，同时保留可追溯证据。

## 当前 Select 的待核查假设

- 首轮 Select 看见完整的已披露原文单位，以及有限的 `UNREAD preview`；预览是原文截片，不是自动展开后的完整记忆。
- 只有模型选择预览或主动 `read_more`，系统才会加载对应完整原文；未选择的预览不会自动成为最终证据。
- 后续 Select 收到新的候选和上一轮选中原文，但当前输入没有明确复述上一轮的 query、阅读请求、证据覆盖缺口和候选来源，存在意图丢失风险。
- 观测账本保留了这些信息，但观测内容没有自动回流到模型语境；因此“可观测”不等于“模型可见”。

## 验证输出

每个 `fresh32-*` 运行保存完整 Add/Search 输入输出、模型调用、Select 菜单、预览、阅读请求、候选排除、闭合和装箱账本。全量完成后再执行 100 次本地 Answer，并按数据集、问题类型和证据阶段分析，不把 Answer 的推断当作 Search 已找到的证据。

若全量结果重复出现“命中一个主题入口但证据集合不完整”，下一步优先实施检索连续性账本：把上一轮 query、已读/未读位置、已满足和未满足的任务形状、补读来源以及新候选的加入原因作为自然叙事输入传给后续 Select，并在最终装箱记录是否保持这些证据槽。该改动不增加额外规划模型调用。

## 执行核对（2026-10-31）

计划已完成：`fresh32-*` 共 26 个独立运行，780/780 Add、100/100 Search 成功；同一批 Search 已完成 100 个唯一 Answer，首次 99/100，唯一长输出截断题使用 16000 completion 上限独立补跑成功。页面已登记并构建，当前研究入口包含本轮运行和完整观测工件。

验证结论与计划假设一致：首轮预览会进入模型输入，但不会自动成为交付证据；40 个双 Select 任务中，末轮输入没有显式连续账本，且 29 个任务至少丢掉了一个首轮选择。下一步仍是先做离线连续性投影和装箱闭合对照，再决定是否修改生产 Search；本轮没有提前改变 Add/Search 方法或历史分母。
