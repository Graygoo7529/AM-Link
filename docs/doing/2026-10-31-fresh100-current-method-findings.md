# fresh32 全量 100 题：当前方法复核记录

日期：2026-10-31

## 运行边界

本轮没有删除历史观测。为了满足“从新起点完整重跑”的目的，使用 `fresh32-*` 建立 26 个独立空数据库，每个数据包只接收本轮自己的 Add；历史运行、旧分母和默认库没有参与本轮检索。这样既得到逻辑上的清空实验，又保留了可追溯的比较材料。

冻结套件是 26 份公开历史、780 个 Add 和 100 个 Search，覆盖 LoCoMo、LongMemEval、PerLTQA、PersonaMem、BEAM 和 CL-bench。真实运行使用 `text-embedding-v4/1024` 与 `gpt-4o-mini`；本地诊断 Answer 使用 GPT-5.4 medium。

## 运行结果

- Add：780/780 成功；Search：100/100 成功。
- Answer：100 个唯一问题均已有结果。首次运行 99/100 成功；唯一失败是一道需要长棋局分析的题，GPT-5.4 达到本地 8192 completion 上限。以 16000 上限独立补跑后成功。补跑没有修改 Add/Search 结果。
- Add/Search 观测中有 4082 个实际模型调用：2505 次 embedding、1577 次 `gpt-4o-mini`；provider 记录的输入分别为 1,540,732 和 3,748,430 tokens，输出为 229,294 tokens（embedding 没有输出 token）。Answer 另有 101 次 GPT-5.4 观测（包括那次被截断的首次调用和一次独立补跑），输入 148,823、输出 69,119 tokens。
- Reflection 观测为 806/810 成功，4 次失败分别是 `model_tool_schema_invalid`、`reflection_sources_invalid` 和 `reflection_notes_limit`。这些失败没有使 Add 失败，符合当前“整理可以不完备、成功 Add 必须原子提交”的边界；但它们仍说明整理输出协议在长尾数据上没有完全稳定。
- Search 中有 103 次 Query、140 次 Select、62 次 `read_more`、4 个模型生成的补充 Query。最终装箱返回 487 个 evidence groups，另有 76 个 group 因字符预算被省略；这不是接口失败，却是证据闭合的真实损失点。

## Select 的实际链路

### 预览确实存在，但不是自动完整展开

99/100 个首轮 Select 输入包含 `UNREAD preview`。这些预览由原文中与问题词汇重叠最高的连续片段截取，最长约 300 字符，仍是原文，不是模型生成的摘要。它们带有原文开头、角色、说话时间和片段内容，所以模型能够理解线索；但未被选择的预览不会自动进入最终证据。

本轮有 42 个预览被模型选择、62 个主动 `read_more` 请求。选择预览的语义是“先把这个候选打开，再参加末轮 Select”，不是“预览本身可以交付”。因此当前链路已经避免了孤立 ref，但没有保证每个重要预览都被展开。

### 多轮 Select 没有共享显式连续账本

40 个问题触发了第二次 Select。首轮平均选择 9.43 个单位，末轮平均选择 7.92 个单位，两轮平均只保留 6.65 个首轮单位；29/40 个问题末轮至少丢掉了一个首轮单位。这个统计不等于每次丢弃都是错误，因为末轮可能用新证据替换重复材料，但它证明当前没有“已覆盖证据必须继续保留”的协议。

更关键的是，40/40 个第二轮模型输入都没有明确出现 `previous selection`、`carry`、`prior selection` 或 `coverage ledger` 一类连续语义。代码把首轮选择作为 `carry` 重新放进菜单，但模型只看到一组新的 `READ originals`，没有同时看到：上一轮查过哪些 query、哪些位置已满足哪个问题槽、哪些 `read_more` 是为补哪一项、哪些候选只是邻文。观测账本记录了这些信息，却没有回流成模型可读叙事。

以 LoCoMo 的“Caroline 参与过哪些 LGBTQ+ 活动？”为例，首轮选择 9 个原文并请求 4 个 `read_more`，末轮只保留 5 个单位，其中仅 2 个来自首轮。GPT-5.4 最终仍给出有条件的部分清单，但它依赖剩余证据和自身谨慎推断；如果被丢掉的单位正好是列表的另一项，Search 已经无法把完整材料交给官方 Answer。

因此，问题不是“模型完全看不到预览”，而是“预览、首轮选择、补读和末轮选择之间缺少可读的共同工作记忆”。这会造成两类现象：

1. 前一轮已经解释过的证据在后一轮只以普通候选出现，容易被重新排序或排除；
2. 新材料进入后，模型不知道它是补充哪个缺口，可能把新材料当成替代品，造成列表不完整、时间条件丢失或主体混淆。

还有一个更细的引用问题：稳定的 `memory:episode/...#start:end` ref 保存在观测映射和工件里，但当前 Select 的正文主要给模型显示本轮的 `[N]` 位置、说话人、说话时间、路由提示和原文。也就是说，模型能读到内容，却不能直接用稳定 ref 识别“这和上一轮是同一段”。这让 `carry` 在程序上连续、在叙事上却像一批重新编号的材料。下一步的连续性账本应同时显示稳定 ref 的可读标签和本轮位置，保持 ref 与原文叙事成对出现。

## 装箱与 Answer 的关系

Search 的 `pack` 是确定性的原文复制和来源标注，能保证交付文本不被模型改写；但 76 个 evidence groups 因 24K 字符预算被省略。若被省略的是候选中低分、但正好承担第二个证据槽的组，Answer 只能做部分回答。GPT-5.4 能在许多题上正确表达不确定性，但它不能恢复没有交付的原文。

本轮还看到一个边界：开放域题有时 Answer 会根据题目和相关背景做合理的谨慎推断，即便 evidence target 没有被召回。这不能算 Search 成功，也不能用 Answer 的流畅度掩盖证据缺口。评估应继续把“Search 已交付证据”和“Answer 根据现有材料作出的判断”分开。

## 根因归纳

当前最明显、且可以泛化到多种数据集的问题有三个：

1. **Select 的集合语义不连续。** `carry` 是程序上的候选复用，不是模型可理解的“已经覆盖/仍缺失”工作记忆。
2. **预览的职责混在阅读和交付之间。** 预览是很好的导航线索，但模型没有稳定的“预览→展开→保留/排除理由”记录；最终结果也没有按证据槽检查完整性。
3. **确定性装箱只保证不改写，不保证集合闭合。** 24K 预算下按组复制会省略材料，且没有将被省略组与已满足/未满足槽关联起来。
4. **模型可见 ref 仍以本轮位置为主。** 稳定 ref 只在观测侧出现，跨轮时不能直接帮助模型对齐同一来源。

Reflection 的 4 次协议失败是另一条工程问题：当前 Add 可以成功、整理异步不完备，但 `sources` 合法性、工具 schema 和 note 数量仍会在长尾输入上失败。它解释了为什么结构化导航在部分数据集上较弱，却不是本轮多跳 Search 低召回的唯一原因。

## 下一步设计方向（本记录不宣称已实施）

下一步应先做一个不增加额外规划模型调用的“检索连续性账本”，作为 Search 内部的模型可见叙事：

- 每一轮 Select 前列出本题的证据槽：主体、属性、时间/状态、比较或排除项；
- 标出上一轮已读、已选、已补读的原文范围及其来源；
- 用自然语言说明每个范围支持哪个槽，哪些槽仍未满足；
- 对新增 Query、邻文和 `read_more` 写明“为补哪个缺口而来”；
- 末轮默认保留已满足槽的最小证据集，模型只能在发现重复或冲突时替换，并输出替换理由；
- 装箱前按槽回看被省略的 group，优先保留能补未满足槽或保留冲突两侧的原文。

这不是增加“必须回答完整”的硬门槛，也不是恢复自由 BFS；它只是把已有观测和 `carry` 变成后续 Select 能读懂的共同语境。应先用当前 100 题的真实轨迹做离线投影对照，再决定是否改生产 Search；若实施，必须以同一 `fresh` 套件重跑，分别报告召回、装箱省略和 Answer 质量。
