## 具体实现

### contains 的“原文对得上”

对于 `episode A --contains--> assertion B`，这条边的每个 source_ref 都必须属于 A 与 B 的来源交集。B 可在其它地方得到更多支持，但那些原文不能证明 A 包含 B。高脚椅的 episode 不能通过另一条环保购物原文连向环保偏好。

预检先给出 `contains_source_mismatch`，不让无效提案驱动无谓阅读；审查修改来源后再次检查，返回 `reflection_contains_source_mismatch` 作为局部内容待办；提交准备也检查，最后提交入口继续拒绝有非法边的整组提案。没有自动翻转/删除边后宣称成功。审查正文仍要判断同一消息中的不同话题是否建立真实联系。

### 工具变小，不取消业务检查

原先每个 FROM、关系类型和所有 TO 组合都展开一份工具子结构，来源枚举也反复复制。现在每个 link 只描述一次 FROM、TO、relation、source_refs、support。非法方向反馈列出这两个实际类型允许的关系，并强调：类型允许不代表原文支持，可以撤销该边。

对上轮 PV4 的 **102 份实际输入中关系工具定义**做同端点/同来源离线投影：总字符从 **1,548,251** 降至 **244,566**，每份降幅中位数 **81.58%**。这是定义字符的离线比较，未调用模型，也不是已测 token/费用节省。新短例节点少，缩减幅度本来就小；完整请求还有正文、其它工具和审查，不能把这个百分比套到整体成本。

### 解释懂了，不等于记忆写对了

共享背景按当前冻结批次解析，不跨会话、不读未来。主归属仍唯一，不把背景作为另一份待处理消息。真实审查中，一个虚构海上救援案例的 detail 正确解释“虚构人物”，持久 text 却仍只有“叙述者救了孩子”，而且只引用助手改写，没有引用说明虚构性质的请求。这个限定语在检索后就容易丢失。

最终提示把“detail 不会成为记忆，限定语必须写进 text”明确到字段描述和逐项输入中，仍未稳定修复该例。另一个混合自述与小说引文的首次留出组件正确保留本人信息、撤销小说工厂经历；不能据此抵消前一个失败。需要同时看解释、最终正文和实际支持来源，不能只看模型理由写得合理。

### 复用格式经历实测收敛

先试独立 `reuse` 数组，再试与新节点同列的短条目，分别出现必填字段遗漏、未读旧目标、旧来源冒充新增、两种条目字段混用。最后一轮控制实验只完成 **5/15** 规划组，较前一轮的 **9/12** 更差；不能因一次 LM04 来源达到4/4就接受这个整理协议。

最终移除简写解析器和工具分支，完整节点格式统一。复用的改进落在调用输入与提交事实：实际阅读完整且同版本、仍在当前投影可见的节点，才出现在明确的复用提示中；正文/时间保护和新增支持联合审查继续生效。真实“新增节点”与“旧正文补支持”在提交后分别记录，网页可见。绝不从模型提出复用推断已成功复用。

本地网页已重建，载入最终 `ground28-lm4-r5` 和 `ground28-controlled-r5` 两份档案及4条持久评注，仍为11数据集/26案例。每题投影最多40个span，明确标记省略数量，完整轨迹不变；加载命令见[可视化入口](../../visualization/README.md)。

## 验证与下一步判断

最终299项回归＋3子测试通过。覆盖共同来源、审查改源、同会话请求背景、旧阅读范围/版本、复用后同 ID 来源增加且不新建 fact、不能借复用覆盖原陈述，以及提交增量与草案的展示区别。已有事务、隔离、幂等、错误边界、真实可见范围等回归继续通过。

本轮852次真实模型调用/852响应，12份新库档案及4份组件档案。最终两个新库档案24/24 Add、11/11 Search，只有11/18规划组完成。LM04来源4/4但只1/3组完成且未触发Select；控制组10/15、无协议失败，但新增来源仍可错误挂到另一项目的旧节点。补来源的程序路径有效，不代表语义补充正确。整体方法未验收。

真实验证包括三个公开数据来源的案例切片、五份人工控制历史及十个审查组件；它们不是大量独立完整公开历史。所有开发失败、源码快照、完整请求和返回均保留在忽略运行目录。不把未分组尾部算失败，也不把已接收但未整理的组算完成。

已观察到的后续难点：用户身份与故事角色仍可能混同；可变 person 正文甚至可能从一人改为另一人；重复/补充/真实替代的判断仍不稳定；审查解释与持久正文的限定语不一致；模型常直接停止 Search，缺乏真实多跳增益证据。应优先对这些断点设计更局部、可核对的任务；本轮没有再引入新的状态机或输出协议。
