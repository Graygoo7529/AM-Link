# Add 失败复核与下一轮改进讨论

2026-10-27，审读基线为用户已提交的 `ee6fe76`。本轮只检查当前源码、已有真实模型输入/返回和数据库；没有新模型调用，没有修改方法、配置或运行数据。下面的建议尚未实施。工程交付及此前真实运行总台账见[收敛实施记录](./2026-10-27-convergence-implementation.md)。

## 结论

近期 Add 的主要断点在 Reflection 的内容决策与收束：规划输出不一致、关系修正没有进展、审查要求继续但没有继续处理的路径。另一个同等重要的问题是部分已成功写入的关系语义错误。增加请求时间、只放宽校验或只看成功率，都不能解决这些问题。

当前请求期限为 1740 秒。R7 的三次失败分别约 10.4、15.7、17.1 秒；最终 R9 的三次失败约 80.3、30.7、24.6 秒，均为方法错误而非请求超时。更早 R1 的网络限制失败另列，不能用于解释最终 R9。

R9 的阻塞位置是计划 `ce1f24e418…` 的组 1（从 0 编号），题为“Legal Definitions and Exclusions in Wrongful Death Settlements”。同一计划的组 0 已提交。后来的 Add 先写入自己的原文与 episode，再继续这个未完成计划，因此再次被旧组阻塞。

关键位置：

- `amlink/engine.py::_add`：发现未完成计划即继续；已触发 Reflection 必须完成目标范围才确认本次 Add。
- `amlink/engine.py::_review_draft`：收到 `needs_revision` 后，在 `check_review` 之前直接抛出 `reflection_review_unresolved`。输出中的局部修改尚未应用，也没有变成下一步的具体待办。
- `amlink/engine.py::_reflection_context` 与 `_run_reflection_group`：再次进入未完成组时清除 pending draft/反馈并从 items 开始。已完成组凭据保留，但未完成组的审查修改不能续做。
- `amlink/local_reflection.py::decode_plan`：检查每个段落归属的组号是否实际存在。R7 的 `groups` 只有一个对象，`primary_groups={p0:0,p1:1}` 因而失败。校验本身正确，生成协议仍脆弱。

失败不表示原文完全丢失。R9 数据库有 4 个 episode、4 个 fact、2 条边；请求状态为 1 个 done、3 个 accepted。部分组已提交，未完成组仍待处理。因此 Search 能返回材料不等于所有 Add 或 Reflection 成功。

## 审查的“需要继续”不只有一种情况

使用当前 `check_review` 对保存的审查 payload/response 做离线校验，没有模型调用或写数据库：

| 输入 | 审查行为 | 当前局部校验结果 |
| --- | --- | --- |
| R7 冰淇淋事件 | 保留原文支持的事件，删除无依据的替代关系；仍返回 needs_revision | 结构合法；仅据输出尚看不出明确剩余工作，显示完成判定歧义 |
| R9 第一次 | 应审查 item 0、relation 1，却返回两个 position 0 的 revise | 非法，不能直接应用；包含疑似把关系当第二条陈述修订的混淆 |
| R9 第二次 | 修改陈述、删除不成立的替代关系；仍要求继续 | 结构合法，但修改内容与不同条件/来源的对应仍需语义核查 |
| R9 第三次 | 8 个待审项，返回位置 0,1,2,3,3,4,4,5 | 非法，重复位置并漏审项目 |

不能把所有 needs_revision 改成 commit。当前错误标签还掩盖了“输出不合法”和“合法修改后仍有实质缺口”的差别，应先分别记录它们，再决定是否存在可执行的局部修订。

## 成功写入也有明显缺陷

R7 把“两人都喜欢看电影”用 `supersedes` 连到“Joanna 喜欢阅读、电影和自然”“Nate 喜欢游戏和电影”。共同兴趣没有否定各自兴趣。数据库确实将两条旧节点设为 `superseded`；旧正文仍在，也仍可被查询，不能描述成已删除。

R9 的两条已提交 `supersedes` 同样把补充条件/说明步骤当成替换。这与当前提示词明确要求“同主体、同属性、同条件、明确替换”不一致。再追加一句同样的抽象规则，没有实测依据保证改进。

R9 待审 fact 常是一段混合多种条件、来源观点和操作建议的摘要。失败审查共给出 19 个候选原文位置；三次相同来源集合展示 10,011 字符，同源范围合并后为 9,271 字符，约 740 字符为重叠范围。第二次修订把全部 19 个位置都作为支持。坐标合法和正文可见，只能证明模型看过这些材料，不能证明每个分句都由它们支持。

此处是研究样本内部陈述的比较，不是在裁定材料涉及的税法。记忆系统可以保存“材料 A 在条件 X 下声称……；材料 B 在条件 Y 下声称……；两者关系尚不能确定”，不应为了输出一个统一结论而擅自消除差异。

## 改进建议：优先减少任务歧义

### 1. 让已有局部审查真正接回局部修改

先验证审查条目，再区分“改后已完成”和“仍有具体未完成项”。对有效修改只作用于未提交草案；明确待办指向哪条陈述、哪个旧对象或哪段缺失原文。用已有 Reflection 预算进行必要的补读或 patch，按修订后的内容完成检查；不要重新生成整组或再叠加一个泛化审查员。

这里建议的是有内容增量的任务推进，不是模型 API 故障重试。重复相同输入、没有证据或草案变化时仍应停止并报错。无效审查不猜测对应关系，不自动当作合法修改。

外部重放或后续 Add 继续同一组时，应考虑保留未提交草案和具体待办；使用前核对计划、原文版本和已修改旧节点版本。已完成组不重复执行。实际工作区恢复设计需要实施前补齐失效条件。

### 2. 将“整理事实”收敛为“整理一组有关联的陈述”

保持原文范围和自然叙事。写入模型先说明当前材料说了什么、属于谁、有哪些条件；旧内容是重复、补充、明确更正，还是不可同时成立。来源标识由程序负责映射，模型主要阅读陈述和支持原句。

fact/event 不必按每句话机械拆分，但应能单独讨论其主体、条件和变化。一条节点同时承载一般规则、例外、流程和建议，会使去重、替代判断、来源对应都更难。

`supersedes` 必须拿出新旧陈述的直接变化依据；主题一致和更详细不是依据。互补材料可并列保留。没有有用关系时允许零边；显式更新、冲突或遗忘仍必须实际处理，不能以删边或 episode_only 掩盖。

### 3. 减少结构输出中的多重编号依赖

规划的主要难点应是划分相关内容，不应是同时维护一份组列表和另一份指向动态组号的表。可研究逐段给语义组标签、程序据此形成组对象等更单一的表示；必须仍然保证每段恰好一次主要归属，不能给漏项猜归属。具体输出协议尚待确认。

审查也应减少“节点编号、关系编号、来源编号”的混淆：输入明确展示待改陈述/关系和允许动作；程序管理标识映射，保留稳定可追踪对应。只改变自然叙事而仍要求同样复杂的编号协调，可能不足以改善合法率。

### 4. 在写入稳定后校准证据集合，而非继续放大窗口

Select 已共用 80,000 字符模型输入预算，按大小分页；但每个 Reference 提供的候选原文段仍有上限（当前最多 4 段）。较大总窗口不能保证关键句进入候选。

R7 四道有来源标注题 top-5 覆盖为 8/14，其中金额 2/4、兴趣 3/7。这是局部来源覆盖，不是回答准确率，也不能全归因于 Select：失败 Add、召回、候选披露、Select、Inspect 和装箱必须逐层定位。

下一步应在冻结候选上检查“每项问题需求—哪段原文支持—哪一步丢失”，保留互补贡献、控制同义重复。模型生成的覆盖说明不是证据真值。Reflection 的 Backlink 在 R7 仍为 0，标准 Search 仅一次；没有充分真实证据证明图探索普遍带来收益，不能靠强制调用次数宣称有效。

## 建议验证顺序与边界

1. 冻结三类反例：已修改仍要求继续、错把补充作替代、分组/审查编号不一致。分别验证改动针对的原因，而不是只比较总成功率。
2. 用新库完整 Add，再独立 Search。当前阻塞组必须能结束；真实冲突仍需保留来源/条件；未解决问题不得伪装成功。旧输入只作组件诊断，不恢复旧库起步。
3. 再扩至不同数据集完整历史，联合报告 Add 完成、陈述与关系质量、最终证据覆盖、真实模型调用和输入规模。不通过增加调用掩盖原有歧义。

本轮完成的是问题复核与讨论提案，尚未实施这些行为调整；未重跑测试套件或模型实验。已有 198 项回归/3 子测试是此前实现的结果，不算本轮新增验证。
