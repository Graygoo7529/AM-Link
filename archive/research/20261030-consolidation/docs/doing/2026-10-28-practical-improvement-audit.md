# 当前切实可行的改进点

2026-10-28。用户已提交迁移，当前基线 `ff706cb`，开始时工作树干净。本轮只读当前源码和 v4 真实轨迹，离线重放审查解码；没有改方法、配置或数据库，没有新增模型调用。以下是建议，尚未实施。

## 优先判断

最有直接证据的两项是：**保持节点语义与支持来源稳定，以及简化 Reflection 审查输出协议**。前者避免整理把记忆改坏，后者避免模型已经生成内容却交付不了。不能把更多节点、更多边、更多模型轮数当成收益。

## P0：阻止派生 episode 被换题改写，区分历史来源与当前支持

最新 `v4-1024-20261028-lm4` 的两次真实提交使用同一 ref：

1. 第一次正文记录 4 月 20 日修车、链条 $25、车灯 $40。
2. 后一次正文变为购买 $120 头盔、对车店满意、将来回店。链条和车灯金额不再出现在这个节点的正文中，语义 ref 仍叫 `bike_maintenance_tune_up`。

原始消息与最低 episode 没有删除，最终装箱也找回了三个金额。因此这是**派生节点的内容与引用语义漂移**，不是原文数据丢失；当前来源召回满分不能证明节点整理正确。

源码原因：`reflection.preflight_mutation` 和 `prepare_mutation` 保护最低 episode、fact/event 正文，但允许其它 episode 被整体改写。另一方面 `drafts.check_review` 对后一次正文只认可头盔来源，`prepare_mutation` 又无条件并回旧修车来源。保留溯源历史的程序规则覆盖了审查对于当前语义支持的判断。

建议先收紧现有 episode 的写入：已经记录的情景不允许换主题覆盖；新事件写新 event/fact，同一事实的复述才复用原节点并增加支持。最低 episode 已提供原文，Reflection 纯同义摘要不应再造一个没有检索增量的 episode。若确有跨消息情景重组，需要明确证明范围与旧内容保留，而不是允许无条件改写。

支持来源按正文判断：对正文完全相同的 fact/event，合并额外支持合理；对允许变化的导航节点，历史曾引用过的原文不自动等于新正文的证据。历史版本仍可从轨迹追溯，不能把被审查排除的来源悄悄重新包装成当前陈述支持。这需要明确最终提交与审查结果的关系，不只是再加一句提示词。

验收：沿真实修车→车灯复述→头盔顺序新库重放，旧节点不丢金额、不换题，新增节点表示正确事件；提交来源与审查认可范围一致。同义复述不增加同义节点，真正新购买仍能新增。分别检查原文完整、事实完整与节点数量。

## P0：简化审查协议，保留严格校验

LM04 那次 `reflection_review_incomplete` 已定位并离线复现。期望 `reviews.u0` 和 `reviews.u1` 并列，实际工具返回将 `u1` 嵌在 `u0` 内。JSON 合法，含有两项意见，但协议位置不合法；当前拒绝提交是正确行为。

该次只有两个审查对象，输入 2190 tokens、输出 202 tokens，`finish_reason=tool_calls`，不是长输出截断或输入预算耗尽。工具 schema 序列化约 4848 字符，整个请求约 12036 字符；增加模型窗口解决不了这一次错误。请求已经设置 strict=true，不能据此假定代理一定执行了结构约束，也不能由本例推断 provider 如何实现 strict。

建议把审查输出做成更浅的固定结构：每个对象只保留自身必要的修改、理由和来源字段，减少每项 keep/drop/revise 分支重复的大量 anyOf、恒为 null 的字段；节点无需填关系专属字段。优先保留一组联合审查，避免为每个小节点额外调用。程序继续严格校验完整性、唯一对象、允许来源、替代依据和修订后的关系端点。

不把错误嵌套“猜成正确位置”，不放宽成漏项即通过，不增加同输入内部重试。单纯换回数组也不算解决方案：历史数组曾出现重复/遗漏编号。应对冻结实际输入比较更简单的 keyed 协议，选择结构稳定且语义检查不退化的输出形态。

验收：覆盖单节点、节点＋边、多个修订、删除节点、明确替代和无增量等不同草案；记录首次结构合法率、最终来源正确性、输入/输出用量。旧错嵌、漏项、重复键必须继续拒绝。冻结组件收益再用新库完整 Add 验证，不等同于端到端已改善。

## P1：审查应守住条件、语气和时间精度

同一最新运行还有语义上的实证：原文说 “I might just go back”，提交正文写成 “The user plans to return”。审查解释为准确保留原文，但从可能变成计划，承诺程度变强。失败审查还把 “April 20th” 改成 “April 20, 2023”，将补入的年份写进声称来自原文的 `time_expression`。即使可结合上下文推导年份，也不能伪装成原句明示。

建议将审查任务聚焦成：读者只看新正文，会不会得到原文未确认的事实？重点对照人物归属、条件、否定、可能性、金额和时间。`time_expression` 作为原句引用应核对实际可见原文；标准化日期必须有清楚依据，不能拿消息日期替代事件日期。保留现在可实际修改草案的能力。

这些规则不意味着再增加整套审查链。先在现有审查中做类型相关的精简提示和确定性引用检查，针对“可能/确定”“建议/承诺”“消息时间/事件时间”正反例验收；不能把引用字面存在当成整条陈述语义成立。

## P1：长节点多片段向量索引

沿用[迁移计划中的设计](../phase-2/2026-10-28-embedding-v4-migration-plan.md#长文本后续实施设计)：一个 MemoryItem 对应多个原文范围向量，Query 后聚合为同一 Reference，命中范围继续进入 Select/Inspect/装箱。

这是有明确结构价值的改进，能够控制单条 embedding 长度，并给局部事实更直接的检索入口；涉及存储和检索聚合，改动比前两项大。当前最大历史输入 v4 实测 6675 tokens，没有新观测证明超限正在阻断这些短例，因此不应排在两个已有真实断点之前。召回提升与调用成本需首/中/尾事实和长短节点混合实验验证。

## Select 与图：先形成有代表性的对照

最新两个 v4 样本没有触发 Select，不能据此判断当前 Select 窗口太小或已经有效。此前 LM04 的三种金额齐全、但复述来源只覆盖 2/4，说明“少选同一事件的复述”不一定是丢了独立事实。下一次应冻结实际候选，分别观察独立事实、事件去重、必要来源和顺序；包含重复车灯费用时，不应为了金标来源数量而把同一笔消费说成多笔。

节点类型与合法关系方向目前已进入工具 schema，`_relation_pairs` 已生成合法组合，不能把“限制关系方向”再写成新功能。历史图的主要问题仍是**类型合法但语义不成立**。当前两个新库零边也不能证明必须强制生边；先确认是否有必要的事件/事实节点、是否有可复用对象、边是否带来新增证据。BFS 增加跳数不会修复错误节点。

建议下一轮先实施两个 P0，并将语气/时间精度检查并入现有审查；先看首次整理成功、旧信息保留、同义重复和模型成本，再决定多片段索引及 Select 的具体改动。无需在这一轮同时扩大所有机制。
