## 3. BEAM：14次Inspect为什么还缺材料

`evidence-20261023-b1-v5`第二批的真实轨迹，step从0计数：

| 步骤 | 实际动作/展示 | 结果 |
| --- | --- | --- |
| 4 | Inspect API限流fact，默认页是它引用的1295字符原文 | 没读这个fact本身的短正文 |
| 5、7 | Inspect缓存fact，先读两页原文 | 来源页优先占用动作和容量 |
| 8→9 | 读取并在下一决策展示缓存fact完整172字符正文 | 此时确实读到目标 |
| 10→11 | 再读长episode；缓存fact正文和其阅读片段不再保留 | 后续提交不能凭“曾经读过”通过 |
| 12→13 | 读取GitHub配置fact的256字符正文 | 此项材料保留到提交 |
| 13 | 再选API限流fact，仍读原文页 | 目标正文依然未补齐 |
| 14 | Mutation | 因API限流和缓存两项旧目标不完整可见被拒绝 |
| 15 | 只剩终结槽，模型再次Mutation | 还缺旧目标，并新增一条不可见来源，轮数耗尽 |

这不是单一的“模型忘记Inspect”。有两条不同断路：**读错层次**，以及**读对后丢失**。`_page_options`以宽泛问题的词面命中排序正文和来源页；长代码比短事实容易命中更多词。`_bound_workspace`又优先逐出非保护Item及其disclosures，保护要到Mutation被拒后才建立，往往太晚。

此外，模型尝试直接改写旧fact；即使通过材料门槛，现有不可覆盖fact/event规则仍可能拒绝。应让模型理解：旧事实作为引用复用，真正更新建立新事实及明确替代关系，不需要把所有读到的旧节点重新提交。

```mermaid
  A[选中缓存fact] --> B[先读两页代码来源]
  B --> C[终于读到172字正文]
  C --> D[随后读取长episode]
  D --> E[容量回收逐出旧正文]
  E --> F[提交时缺材料]
  F --> G[只剩终结槽，无法补读]
```

## 4. 三个本地反例：展示账本尚未统一

忽略目录中的`amlink/data/diagnostics/reproduce_visibility_20261023.py`对当前生产函数进行无模型复现，结果保存到同目录的`visibility_reproduction_20261023.json`。这是诊断反例，尚未作为修复后的新增回归。

1. **默认页层次不合任务。** 31字符fact正文及3037字符相关原文，默认Inspect页落在raw来源，fact正文排在后面。Search按问题读来源有意义；Reflection为了维护该节点时，通常应先了解节点本身。
2. **不可见又不可重读。** 完整页留在内部disclosures，但被较小的最终投影省略；`_page_options`仍按内部disclosures排除该页。实际结果为`body_visible=false`且`body_offered_for_reread=false`。这违反原计划“隐藏后允许重读”的要求。
3. **输入中有全文，账本仍报缺。** 完整正文位于`context.items[ref].text_fragment`，且已有同版本读取标记；`_record_visible`仅接收`context.disclosures`，门槛仍返回`same_version_inspect_full_body_in_final_call`。References的证据片段与sources也有类似的表示分裂风险，需统一审计。

修复不能简单取消先看再写。应分别记录明确读取动作的范围、最终请求实际可见的范围，以及历史展示回执；这些事实互不冒充。仅有摘要、ref或版本hash不能算正文已读。

## 6. 0边的进一步定位：关系提出后也会消失

8次轨迹共提出**18条关系**（含未提交提案中的重复尝试，不是18条独立真实关系）：12条所在提案先被材料门槛阻断；其余6条进入Mutation准备，全部被`relation_type_mismatch`过滤。最终0边与数据库一致。

例如L04最后获准提交的提案包含：

- `person Joanna --about--> person Nate`
- `person Nate --about--> fact MoviePreferences`
- 两条`person Nate --contains--> event ...`

当前关系语义要求`fact/event --about--> person/...`，`contains`则是`episode --> fact/event`。BEAM另两条是`event --contains--> fact`，同样不合法。不能据此推断数据里没有关系，也不能为了增加边数直接翻转或发明关系。

目前`prepare_mutation`记录`filtered_links`并继续提交节点，水位正常推进。这使“Add成功但关系未建立”成为真实情况；材料门槛的`accepted=true`也不表示关系接受。可视化应拆开材料检查、节点准备、关系接受/过滤、事务提交四个结果。

建议把合法方向与具体类型成对呈现，使用可追溯的事实/事件作为人物间关系的中介；错误关系在提交前向同一个有界loop反馈。是否将类型错误改为阻止整批提交，是下一方案明确列出的行为变更，当前尚未修改。

## 7. 缓冲误触发：update cache不是记忆更新

B01 v5两个Add均因`explicit_change`触发Reflection。第一批ordinal6命中`update the`，上下文是“making enough requests to **update the cache regularly**”。这是程序缓存刷新，不能证明已有记忆被明确更正。第二批ordinal8的“update my API key settings ... new daily quota of 1,200”才是需要检查新旧约束的变化候选。

因此虽然代码设置普通情况至少两个Add，宽泛正则仍绕过了积累。下一步应把词面线索与确定性的会话/容量边界分开：词面线索提示模型关注变化，不能一律作为立即整理的事实。阈值8条/6000字符本身尚无跨数据集最优性证据。
