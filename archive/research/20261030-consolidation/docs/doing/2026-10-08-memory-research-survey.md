# Add/Search 记忆研究调研综述：从数据难点到可观测证据链

日期：2026-10-08；状态：本轮调研与跨数据集 Mem0 诊断 done。

## 1. 范围和证据边界

本轮以本机已核验的公开来源为对象：LoCoMo、LongMemEval、BEAM、PerLTQA、CL-bench / Life、PersonaMem-v2、PersonaMem-v3 和 MemoryAgentBench。数据层将原始材料、方法可见历史、当前任务、作者标注和人工案例解释分开；案例库现在有 26 个案例。完整结构扫描、BM25 对照和来源限制见 [`2026-10-07-dataset-research.md`](./2026-10-07-dataset-research.md)。

本轮真实模型实验只使用公开样本的明确切片，不把答案、rubric、ground-truth preference 或 evidence 注入 Add。新增 Mem0 运行使用 Mem0 OSS 2.2.1、gpt-4o-mini、embedding-3 / 512 维、本地 Qdrant，关闭 SDK 重试；原始输入、快照、请求和观测保存在被 Git 忽略的运行目录。

- 跨数据集切片：6 个案例，14 次 Add、6 次 Search、5 次 Answer；49 次 provider 请求，106,607 input tokens，0 次 provider 层失败。1 次 BEAM 冲突 Add 被 Mem0 报 `LLMError`，该查询未进入 Answer；它不是“空记忆成功”。
- BEAM 冲突重跑：1 个案例，1 次 Add、1 次 Search、1 次 Answer；5 次请求、9,088 input tokens，全部成功。
- 费用没有可靠计价，因此记为未知。切片由研究者按案例证据选择，不是独立测试集，也不能推出总体准确率。证据覆盖和回答审查分别报告；Search 成功不等于 Answer 正确。

## 2. 数据集真正考察的不是同一种“记忆”

| 难点层 | 数据中的具体形态 | Add 应保存 | Search 应交付 |
|---|---|---|---|
| 结构与边界 | PerLTQA 的 profile / relation / event / dialogue；CL-bench 的材料与任务边界；BEAM 的 chat、代码和探针混合 | 来源类型、主体、说话者、顺序、原始 ID | 与问题类型匹配的原文片段，不能把 rubric 或答案写入历史 |
| 时间与更新 | LongMemEval 日期、相对时间、最新值；LoCoMo 跨会话日期；BEAM 配额更新 | 事件时间、提问时间、有效期、旧值与新值、更新来源 | 当前状态和必要的旧值/日期，不能用写入时间替代事件时间 |
| 主体与关系 | LoCoMo 两人交集、PerLTQA 有方向关系、PersonaMem 他人信息 | subject、object、关系方向、归属和来源 | 先保证主体隔离，再做交集或多跳；同名不等于同一人 |
| 聚合与推理 | 金额去重、分子/分母、时间间隔、MemoryAgentBench 三跳 | 可组合的原子事实和事件身份；重复提及与真实事件分开 | 找齐完整证据链并保持单位/口径，不能只返回最相似的一段 |
| 冲突与拒答 | BEAM “已取得 / 从未取得”；LongMemEval 拒答；PerLTQA 源材料日期矛盾 | 相反陈述、来源、状态和未决关系 | 同时返回冲突两端；证据不足时支持澄清或拒答，不强行覆盖 |
| 隐私、遗忘和许可 | PersonaMem-v2 sensitive_info / ask_to_forget；PersonaMem-v3 继续帮忙但不长期记住 | 记忆许可、作用域、删除/失效状态；敏感原文默认最小化 | 过滤已撤回内容，不能把当前任务敏感值或旧向量重新返回 |
| 反馈与推荐 | PersonaMem-v3 活动、停留、跳过、future held-out 反馈 | action、内容身份、时间和置信度；不把生成标签当事实 | 只看 query 前活动，区分看过、停留、喜欢和厌恶 |
| 长度与噪声 | LongMemEval S/M/Oracle、BEAM 100K–10M、PersonaMem 32K/128K | 可扩展的分层事实和可追溯原文，而非单一摘要 | 先缩小相关范围，再补齐证据；报告裁剪、排序和预算 |

因此，记忆方法的基本单位不能只是“文本向量”。至少要能表达：**谁的什么事实、发生在何时、在什么范围有效、来自哪段原文、当前状态是什么**。摘要可以提高可用性，但必须能回指原子证据；否则 Answer 可能说对了，却无法证明为什么对。

## 3. 统一的理论链路

**Add** 先做边界判断，再写入可追溯事实：识别 role / subject / event，保留来源和时间，建立 `supersedes`、`contradicts`、`expires` 或 `forgotten` 状态。它不能读取作者答案或 rubric 来“修正”历史，也不能把助手对他人的描述自动变成用户偏好。

**Search** 不应只做一次相似度排序。复杂问题应拆成证据需求：金额题需要项目、金额、重复事件和时间；比例题需要同口径分子和分母；交集题需要两个人各自的证据；冲突题需要两端陈述；推荐题需要 query 前的正负线索。返回结果应带来源、时间、归属、状态和未选候选原因（若可观测），由 Answer 决定是否足够。

**Answer** 只消费 Search 实际交出的上下文。它负责计算、去重、排序、条件分支和澄清；记忆层不应把“看起来合理的答案”伪装成证据。评估要分成字面证据命中、完整证据链、回答正确性、延迟和实际调用量。

这条链路也就是设计检查：每个阶段都问“事实是否被保存”“必要证据是否返回”“回答是否越过证据边界”，并在观测里记录未知，而不是把未采集写成成功。

## 4. Mem0 跨数据集实测：正确回答与失败位置

| 案例 | Search / Answer 现象 | 归因 |
|---|---|---|
| LM04 支出去重 | 回答 `$65`，只合并了链条 25 和车灯 40，遗漏头盔 120；此前返回记忆中可见头盔事实 | 抽取和检索没有形成“3 项独立事件 + 重复车灯”的结构；回答也没有核查证据集合 |
| LM05 分子/分母 | 正确回答 20%，使用 20 / 100 | 短片段中事实足够；仍需把两个来源一起交给可核验 Answer |
| LM06 偏好迁移 | 返回屋顶泳池/阳台热水浴缸偏好，但没有景观偏好，也没有具体酒店 | 偏好部分迁移成功；证据标记的完整覆盖为 0，推荐质量不能由此判定 |
| LoCoMo L04 | 给出电影和甜点作为 Joanna/Nate 共同兴趣；7 个来源只返回 top-5 | 初步回答合理，但多人物交集的证据覆盖不足，不能称完整正确 |
| BEAM B01 | 正确回答每日 1,200 次 | 明确更新样本适合当前状态检索；本题没有统一 turn-level gold |
| BEAM B02 重跑 | Search 返回“尚未取得”和“3 月 10 日已取得”；Answer 说“已取得”，没有提示矛盾 | 召回链路成功，冲突识别和回答协议失败；这是最清楚的 Add/Search/Answer 分界例 |

LM04 和 LM05 的对照说明：**“召回到了相关句子”不等于“形成了可计算的记忆结构”**。B02 更进一步说明：**Search 返回两条相反事实仍不保证 Answer 会澄清**。因此 AM-Link 需要将证据关系和冲突状态交给官方 Answer/Eval，同时在本地观测中记录它们是否被返回。

此前六条件 Mem0 短例提供了互补结论：更新题回答正确但新旧记忆并存；日期题即使在正文前加入来源日期仍不能完整计算；拒答题能保留类别边界；他人信息未出现明显错归，但统一 Answer 提示过严；遗忘题没有真正激活删除验证。两批实验都不是全量准确率。

## 5. 对 AM-Link 二期设计的直接建议

1. **用事实与事件双层模型。** 事件保留原文、时间、主体和来源；事实层保存当前值、旧值、冲突、有效期和删除状态。重复提及先链接事件，不要立即合并成一次事实。
2. **让 Search 接受证据需求。** 在内部把查询拆成 `entities / attributes / time / state / required_sources`，但输出仍只返回证据；为每条结果保留 source、score、state 和 relation。
3. **把冲突当一等结果。** 同一属性出现否定、更新或不同主体时，不用最后写入覆盖；返回冲突集合和澄清提示所需的来源。
4. **把隐私和遗忘做成可检查状态。** Add 记录拒写/删除范围，Search 记录过滤和残留候选；敏感字段不得出现在 Answer 上下文或长期画像中。
5. **观测从真实调用生成。** 每次 Add / Extract / Store / Index / Search / Retrieve / Context 都记录 parent span、输入输出 artifact、来源关系、模型调用、延迟、token 和错误。没有埋点的阶段显示 unknown；不要由 HTTP 200 推断抽取成功。
6. **先用案例切片，再做组隔离验证。** 设计案例只能形成机制假设；方法调整后必须使用未参与设计的人物/历史组，并同时报告证据链、Answer、延迟和费用。

## 6. 局限与下一步

本轮切片数量小、来源由案例研究者选择，不能代表数据集分布；Mem0 使用一个固定 prompt、单一 embedding、top-5 和本地 Qdrant，未运行官方 judge。BEAM 的部分任务仍无统一来源标注，CL-bench / PersonaMem 的 rubric 和敏感标签只用于解释，不是记忆输入。下一步应把同样的观测接口接入二期真实 Add/Search，先在 LM04、B02、PV04 三类案例上做结构化状态实验，再选未参与设计的记录做 holdout；若要比较 Mem0，应固定切片、模型、预算和 Answer 协议，并把依赖失败单列。

本报告与案例网页共用 `casestudies/catalog.json`。本地完整页面可用 `python -m visualization.build --local --workspace --web` 重载，不会重跑模型。

## 7. 为什么“记住了”仍然答不对：一条容易断开的链路

可以把一次正确回答想成六个连续的抽屉。每个抽屉都要交出下一步需要的东西；只要有一个抽屉空了，最后的回答就可能看起来流畅，却没有事实支撑。

```text
原始对话
  ↓ ①识别边界：谁说的、在什么时候、是事实还是请求
可检索事件
  ↓ ②保留状态：旧值/新值、冲突、重复提及、撤回和有效期
可组合事实
  ↓ ③提出证据需求：要哪些人、属性、时间、分母、来源
候选集合
  ↓ ④补齐与筛选：收齐必要证据，去掉未来、越权和被撤回内容
回答上下文
  ↓ ⑤计算/比较/澄清：去重、求交集、算比例、处理条件和矛盾
答案
  ↓ ⑥核验：每个结论能回指来源，不能把未知写成确定
```

### 7.1 六个抽屉分别缺什么

| 抽屉 | 缺失时的表面现象 | 实际断点 | 应补的处理 |
|---|---|---|---|
| ① 边界识别 | 把猫的名字回答成仓鼠名字；把他人的兴趣算成用户偏好 | 主体、角色或任务边界丢失 | Add 保存 `subject / speaker / object / source_role`；对当前任务和长期画像分开 |
| ② 状态保留 | 新旧值都在，但不知道哪个“当前”；相反说法被最后一句覆盖 | 没有 `supersedes / contradicts / expires / forgotten` 状态 | 为同一属性建立版本链；更新和矛盾走不同分支 |
| ③ 证据需求 | 找到 20，却算不出百分比；找到一个人的兴趣，却说两人共同拥有 | Search 只按整句相似度，没拆子问题 | 先生成证据需求清单：分子、分母、人物 A/B、时间窗口、事件身份 |
| ④ 补齐与筛选 | 相关记忆存在，但被 top-k 截掉；未来反馈泄漏进历史 | 预算、排序或时间切片错误 | 先召回候选，再按关系/时间/来源补齐；保留未选候选与截断原因 |
| ⑤ 推理与澄清 | Search 已返回两条矛盾事实，回答却选一条；重复消费被重复相加 | Answer 没有执行关系运算或冲突策略 | 对金额去重、比例计算、交集、条件分支和冲突澄清建立显式步骤 |
| ⑥ 回指核验 | 说得像正确答案，但没有证据；摘要改写后无法追溯 | 记忆正文和来源脱钩 | 每个事实/摘要绑定来源 ID、时间和原文 artifact；评估同时看答案与证据链 |

### 7.2 真实案例：LM04 为什么会从 185 变成 65

理论目标是：链条 25 美元、车灯 40 美元、头盔 120 美元，共三笔独立消费；车灯在历史中被重复提到两次，应该只算一次。

本次 Mem0 回答是 65 美元。观测中可以看到它已经形成了链条和车灯的记忆，也形成过头盔记忆，但最终回答只使用了前两项。断点不是“完全没有记住”，而是：

1. Add 没有把四次提及和三次消费事件显式区分；
2. Search 没有返回一份“应核对的消费事件清单”；
3. Answer 没有在求和前检查“是否还有同类金额/物品未纳入”。

要打通，Add 至少需要保存 `event_id / item / amount / time / mention_of`；Search 需要返回三项事件及车灯的重复关系；Answer 才能执行“按事件去重后求和”。只增加 top-k，可能得到更多相似句子，却不一定得到三项可计算事实。

### 7.3 真实案例：LM05 为什么容易少一个分母

问题问女性占领导岗位的百分比。历史分别出现“女性领导岗位 20 个”和“领导岗位总数 100 个”。Mem0 本次回答正确地算出 20%，但它之所以能答对，是因为切片很短、两个数字都在可用上下文中；这不代表方法已经掌握了比例问题。

完整历史里，检索很容易只返回包含“女性、领导、多样性”的句子，遗漏“总数 100”。因此正确链路必须把问题拆成：

```text
分子 = 女性领导岗位数 = 20
分母 = 同一公司、同一时间、同一口径的领导岗位总数 = 100
校验 = 20 和 100 是否属于同一统计对象
计算 = 20 / 100 × 100% = 20%
```

如果缺分母，系统应返回“找到女性岗位数，但还不能计算比例”，而不是猜一个百分比。

### 7.4 真实案例：BEAM B02 为什么“召回正确，回答仍错”

冲突历史同时说“3 月 10 日已经取得 API Key”和“从未真正取得 API Key”。单例重跑中：

- Add 成功，记忆快照同时保存两条相反陈述；
- Search 成功，前五项中同时出现“尚未取得”和“已取得”；
- Answer 却只说“你已经取得”，没有说明矛盾，也没有请求澄清。

这说明链路已经走到证据集合，但没有进入“冲突状态处理”。如果把 Search 结果直接拼到普通问答提示里，模型往往会选择语气更肯定、日期更具体或排序更靠前的一条。正确做法是让检索输出显式关系：

```text
事实 A：已取得，来源 0:32，状态 candidate
事实 B：从未取得，来源 0:70，状态 candidate
关系：A contradicts B
回答策略：不选单方结论，指出矛盾并请用户澄清
```

因此冲突不能只靠“把两条都返回”解决；需要 Search/Context 阶段保留关系，Answer 阶段执行澄清策略。AM-Link 仍只负责交证据，但二期埋点应能观察是否把 `contradicts` 关系交给回答侧。

### 7.5 真实案例：LM06 和 LoCoMo L04 说明“相关”不等于“完整”

LM06 的酒店问题中，Search 找到了“屋顶泳池、阳台热水浴缸”等偏好，却遗漏“好景观”。这不是完全没找到偏好，而是证据覆盖不全；如果 Answer 仍然给出确定推荐，就会把部分上下文当成完整用户画像。

LoCoMo L04 要求求出 Joanna 与 Nate 的共同兴趣，作者标记了 7 个来源。一次只返回 5 个候选时，回答说“电影和甜点”，可能是合理的局部答案，但无法证明没有第三项共同兴趣。这里需要一个覆盖检查：每个角色至少有一组证据，交集中的每个结论都有来源，未覆盖的来源不能被默认为“不相关”。

### 7.6 时间、遗忘和敏感信息的特殊断点

- **时间**：LM02 中，把系统运行日当成“今天”会制造假日期；即使把会话日期加进正文，若抽取阶段仍压缩成“最近”，Answer 也无法计算间隔。必须同时保存事件时间、时间粒度和时区假设。
- **遗忘**：PV04 中回答没有提到被忘记的手工艺偏好，不等于向量、摘要和缓存已经删除。要证明遗忘，必须在 Add 观测中记录删除范围，在 Search 观测中检查旧证据是否仍是候选，并在 Answer 上下文中确认不再出现。
- **敏感信息**：PV03 的保险理赔问题可以当场帮助用户，但社会安全号码、完整地址等不应变成长期画像。若只在 Answer 阶段遮盖，Add 已经泄露就太晚；最小化必须发生在 Add 之前或写入边界。

### 7.7 让链路真正可用的最低实现

一个能稳定支持这些案例的二期方法，至少应具备以下能力：

1. **来源化写入**：每条记忆都有原文来源、角色、事件时间、用户范围和状态；摘要不能脱离原文。
2. **状态化组织**：支持更新、冲突、撤回、过期和重复事件，不以最后写入简单覆盖。
3. **需求化检索**：查询先分解为主体、属性、时间、关系和证据需求，再做候选召回与补齐。
4. **证据化上下文**：交给 Answer 的每条内容都带来源、排序、关系和是否满足某一证据需求。
5. **显式推理策略**：对去重、比例、交集、时间差、条件答案和冲突澄清分别处理；不能只依赖通用 prompt。
6. **失败可见**：抽取失败、依赖失败、空结果、证据不足和 Answer 拒答使用不同状态；每个未知都能在观测中定位。

这六点打通后，记忆系统才从“能找到一些相关句子”升级为“能交付足够、可验证、不会越界的证据”。最终回答是否正确仍由官方 Answer/Eval 决定，但 AM-Link 可以清楚说明：缺的是事实、状态、证据、排序、推理，还是外部依赖。
