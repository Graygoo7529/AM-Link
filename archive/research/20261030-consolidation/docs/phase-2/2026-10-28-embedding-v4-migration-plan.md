## 长文本：本轮分析边界

v4 的 8192 tokens 上限按单条文本计算，10 条批量限制不能代替长度限制。当前最低 episode 保留完整消息，整体一次 embedding；原文长度预算采用字符，不能据此证明符合 token 限制。不能直接用 gpt-4o-mini 的 tokenizer 或旧 embedding-3 的用量替代 v4 的计数。

本轮先检查实际历史输入的规模分布，并用公开长材料测试 v4 的实际边界。超限必须保留明确失败，不能悄悄截断、换回旧模型或让必要索引失败的 Add 返回成功。完整长文本索引需要单独设计后实施，不在配置迁移中隐含改变检索语义。

建议设计：MemoryItem 与原文保持不变；向量索引将长节点按自然段/消息边界分为多个带原文坐标的片段，每片各有向量，Query 命中后聚合为同一语义 Reference，并将命中范围交给既有披露/Select。需要同步设计分段长度依据、跨边界衔接、单节点多命中的聚合规则、更新/遗忘原子性和索引版本。不能先平均全部分段向量便宣称证据范围问题已解决。

## 长文本后续实施设计

真实边界已核查：上轮最长 episode 是 11,198 字符，v4 实测 6,675 tokens；另 9,001 tokens 合成输入虽被智增增接受，仍不能据此提高官方 8,192 上限。下一步应保持原文完整，将切分限定在索引表示层：

1. **长度依据**：先核实与供应方兼容的 Qwen3 tokenizer，并用中英、代码、特殊字符对照响应 usage。预留标题/分隔符预算。不能用“每字符约几个 token”做硬保证；计数依据尚未核实时，不宣称已实现严格上限保护。
2. **分段范围**：长最低 episode 优先按原消息和自然段切分；单条超长消息再按句边界切，必须保留 Item 原正文的 `[start,end)`、文本 hash 和完整覆盖。只给边界少量相邻上下文，避免把整批共同材料重复到每段。短节点保持一个片段。
3. **索引身份与原子性**：向量从当前 `(user,ref)` 唯一键改为 `(user,ref,片段位置)`；指纹加入分段规则版本。所有片段嵌入完成后才提交 Add；修改节点或授权遗忘同步处理全部片段。批量仍最多 10 条，不叠加内部重试。需要明确升级 schema，并按项目约定从新库开始。
4. **Query 聚合**：各片段参与向量召回，按 ref 合并；初始采用最高片段相似度作为节点分数，避免长节点凭片段数挤占候选。保留多个互补命中范围，和 BM25 命中一起交给 Reference；不平均全部向量抹平局部信息，不凭片段数增加节点票数。
5. **披露与证据闭合**：Reference 展示命中片段及可读上下文；Inspect 能沿原文坐标补读相邻范围；Select 使用现有覆盖传播；最终证据仍从原文取回。片段不是新增 MemoryItem，不增加图节点和关系复杂度。
6. **验收**：短文本检索保持一致；长材料首/中/尾事实和跨切分边界分别测召回；第二批向量失败时 Add 零写入；更新/遗忘不能遗留旧片段；观察长节点占比、每次 Add 向量数量、调用延迟与 token 成本。先验证这一方案，再讨论是否需要额外的整篇导航向量。

该设计尚未写入主方法。当前必要 embedding 失败仍明确失败且不接收该 Add；不会把未覆盖的全文当作已经完整索引。
