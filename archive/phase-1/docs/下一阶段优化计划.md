# ADD/Search 下一阶段优化计划

## 目标与边界

本阶段继续遵守 [设计理念.md](../设计理念.md) 和赛事 Add/Search 边界：原始消息是唯一事实真源，Search 只返回可追溯证据，不生成最终答案；所有结构化节点必须关联同一 `user_id` 下的 source event。优化目标是提高 evidence recall、MRR 和多跳链完整性，同时保持 Add 幂等、立即可检索、用户隔离和可降级。

本阶段不引入自由 Agent 循环，也不改动对外协议。模型调用仍固定为一次受 schema 约束的 Add maintenance 和一次 Search query plan；图扩展、路径选择、去重和时间过滤由确定性代码完成。

## 问题假设

1. **多跳短板主要在 Search 组织证据，而非单纯缺少向量。** 当前 graph 是从前 20 个种子做两跳平面扩展，再统一 RRF；同一条关系链上的节点没有得到完整性奖励。
2. **single-hop 短板来自查询词与原文词面不一致。** Query planner 只能在模型可用时提供扩展；planner 失败时的确定性 token 化没有实体别名和问句谓词抽取。
3. **派生节点会竞争 Top K。** fact/entity/concept/raw 可能都对应相同 source event；仅用 `evidence_group_id` 还不足以表达“直接证据优先、派生摘要择一”。
4. **Add 结构化成本偏高。** 当前启用模型后每个新 Add 都尝试 maintenance；设计理念中的事件/字符/token 阈值尚未成为真正触发条件。

## 优化路线

### P0：Search 证据链重排

1. 保留 lexical、semantic、temporal 和 planner 的候选召回，新增 `EvidencePath` 内部结构：记录 seed、link relation、hop、source event 集合和 query term coverage。
2. 对 multi-hop/关系型 query 构造最多两跳候选路径；路径分数同时考虑路径长度惩罚、节点相关性、关系匹配、source event 覆盖和时间一致性。
3. 排序时使用“直接证据 + 完整路径”配额：先保证每条高分路径至少保留一个直接 source，再补齐尚未覆盖的链节点，最后才填充普通相似节点。
4. 只在内部做路径计算，外部仍返回官方允许的 `{id, content, score, created_at}`；不得返回答案或金标信息。

验收：在固定 3-sample manifest 上，multi-hop recall@10 >= 0.20、chain coverage@10 >= 0.20，overall recall@10 不低于基线；若单跳或 adversarial 下降超过 0.03，回滚权重。

### P1：派生证据折叠与直接证据优先

1. 将 `evidence_group_id` 从“同一 canonical fact”扩展为 source-event overlap 组：共享超过阈值 source event 的 fact/entity/concept/raw 进入同一竞争组。
2. 组内选择规则固定为 `raw/daily > fact > entity/concept`，但 fact 的 query relevance 明显更高时允许替换；同组不重复占位。
3. 对多跳路径使用“组内代表节点 + source event 映射”，避免折叠后丢失链条所需的不同 source event。

验收：duplicate rate 保持为 0；结果中同一 source-event 组最多一个代表，multi-hop 链节点不因折叠全部消失。

### P1：查询理解的确定性增强

1. planner 可用时让模型只输出 retrieval queries、实体、谓词、时间和候选 ID；不改变最终证据内容。
2. planner 不可用时增加轻量确定性规则：问句谓词词组、数字/日期、实体别名、否定词和中英混合 token；不做开放式 LLM 改写。
3. 对每个扩展词保留来源标签，防止低置信扩展词压过原始 query。

验收：single-hop recall@10 >= 0.20；adversarial recall@10 不下降超过 0.03；无 planner 与 planner 两条路径均有回归测试。

### P2：Add maintenance 阈值与成本控制

1. 为每个 user 保存 `last_maintenance_event_count`、watermark 和累计字符/token 估计。
2. 只有达到事件数、字符数或高置信变更触发条件才调用 maintenance；未达到条件时仍写入 raw/working/FTS 并保持立即 Search。
3. 删除、冲突、明确偏好变更等高价值指令可绕过普通阈值，但仍使用同一严格 mutation schema。
4. maintenance 失败不影响 raw；失败 job 保留有限重试和退避，不重复创建结构节点。

验收：相同 LoCoMo Add 回放中模型调用数显著低于“每 Add 一次”，raw recall 不下降；sync Add 的协议时序保持不变。

### P2：时间与冲突排序

1. 将 source timestamp、event time、valid time 分开参与排序；明确 historical/current 查询不得互相污染。
2. 对相同 canonical key 的版本使用 source freshness、valid interval 和 query intent 组合排序；tombstone 在所有召回通道统一阻断。
3. 增加跨 session、相对日期和冲突事实的固定回放样例。

## 实验矩阵

每次只改变一个变量，并保留同一 manifest、同一 `top_k=10` 和同一数据库初始化方式：

| 实验 | Add | Search | 目的 |
| --- | --- | --- | --- |
| A | lexical | 当前融合 | 固定基线 |
| B | lexical | 路径完整性重排 | 验证多跳假设 |
| C | lexical | B + source-event 折叠 | 验证派生节点竞争 |
| D | threshold maintenance | C | 验证 Add 成本与结构质量 |
| E | embedding-3 | C/D | 验证同义和长距离召回增益 |
| F | 官方 `gpt-4o-mini` | C/D/E | 只作为正式 Full 候选，不用调试模型冒充成绩 |

每个实验记录 overall/category recall@1/5/10、MRR、multi-hop chain coverage、duplicate rate、Add/Search p50/p95/max、provider 调用数和错误降级次数。所有结果必须标注模型、prompt 版本、配置和 commit。

## 执行顺序与停止条件

1. 先实现 P0 的路径内部结构和离线/单元测试。
2. 在固定 3-sample LoCoMo 切片上跑 A/B/C，只有 B 或 C 提升多跳且不损害其他类别才继续。
3. 使用 Fake provider 和真实 provider 回放校准 P2 maintenance 阈值，比较调用数和 recall。
4. 最后使用真实 embedding-3 和可用的官方 `gpt-4o-mini` endpoint 做小规模复核。
5. 任一改动导致协议测试、用户隔离、Add 后立即 Search、tombstone 或 adversarial 指标回退，立即回滚该实验，不进入提交版本。
